# Phase 08: macOS Native App - Context

**Gathered:** 2026-09-17
**Status:** Plans 01-03 executed; Plan 04 (signing + distribution) ready for execution
**Source:** User-supplied tech spec (inline), plus four scope answers given interactively

<domain>
## Phase Boundary

Add a native macOS client that SENDS files through send.gemba.uk: pick or drop files →
client-side encrypt → upload → one share link. Cross-compatible with the web app in both
directions (a Mac-made link opens and decrypts in a browser, and vice versa). Includes a
Finder/Share-menu extension and the Developer ID signing + notarization path.

Excludes: receive/download in the app, any change to the web app, any change to the wire
format, and the Mac App Store route.

</domain>

<decisions>
## Implementation Decisions

### Scope (LOCKED — user answers, 2026-09-17)
- **Send-only, full parity.** Password, expiry, download limit, recipient verification and
  email notify all present. No in-app download.
- **All four build phases in one pass:** crypto core, upload client, SwiftUI app, Share Extension.
- **Location:** `macos/` at the repo root, sibling to `android/`.
- **Signing:** build unsigned (ad-hoc) first; Developer ID + notarization as a follow-on —
  revised 2026-09-17 when the user confirmed an Apple Developer account exists (Plan 04).

### Crypto contract (LOCKED — must byte-match `src/lib/crypto.ts`)
- AES-**128**-GCM, 16-byte key, 12-byte random IV per file, packed `[IV][ciphertext][tag]`,
  key base64url-unpadded and only ever in the link fragment.
- CryptoKit's `AES.GCM.SealedBox.combined` IS that layout, so neither side re-lays it out.
- Test vectors are GENERATED from the web's own WebCrypto path, not hand-written, so the Swift
  implementation is checked against the web implementation rather than a second reading of the spec.

### Architecture (LOCKED)
- One Swift package (`GembaKit`) holding `GembaCrypto` + `GembaUpload`, linked into BOTH the app
  and the extension — exactly one implementation of the wire format.
- The Share Extension does the whole encrypt→upload→link job itself rather than handing files to
  the main app through an App Group. An App Group container needs a real provisioning profile;
  self-contained needs none and is one step fewer for the user.
- The `.xcodeproj` is GENERATED by `scripts/generate-project.rb`, not hand-maintained, so build
  configuration is reviewable as code and cannot drift from the sources.

### Constraints (LOCKED)
- Encryption boundary unchanged: the key never reaches the server, with the same single exception
  the web app already has (the notify email carries the link, fragment included).
- No third-party crypto. CryptoKit only.
- Design fidelity: colours, radii and spacing come from `design-system/tokens/` and the `.dark`
  block in `src/app/globals.css`. Nothing invented.
- Server contracts are mirrored, never renegotiated: part uploads write no metadata, and
  `/api/files/finalize` owns the single meta write and the single counter seed.

</decisions>

<constraints>
## Platform Realities Discovered During Execution

- **No incremental AES-GCM exists on this platform.** CommonCrypto's GCM entry points
  (`kCCModeGCM`, `CCCryptorGCMSetIV`, `CCCryptorGCMFinalize`) are absent from the macOS 26 SDK,
  and CryptoKit's `AES.GCM.seal(inPlace:)` is macOS 27+ while this app targets macOS 14. A
  streaming encryptor was written against CommonCrypto, failed to compile, and was removed.
  Encryption is one-shot with a memory-mapped plaintext and the ciphertext written straight to a
  temp file that uploads from disk — peak memory ~1 ciphertext vs the browser's ~3 copies.
- **There is no Swift client for Vercel Blob.** `BlobClient` speaks the `@vercel/blob/client`
  protocol directly and pins two constants from that package: the API URL and `x-api-version: 12`.
  Both need rechecking if `@vercel/blob` majors.
- **Multipart is deliberately not used.** The web uses it because a browser tab can die mid-upload;
  URLSession uploads from a file on disk, so a single PUT is simpler and produces an identical blob.
- **Xcode injects `get-task-allow` into signed builds by default**, which notarization rejects.
  Release sets `CODE_SIGN_INJECT_BASE_ENTITLEMENTS = NO`; Debug keeps it or the debugger cannot attach.
</constraints>
