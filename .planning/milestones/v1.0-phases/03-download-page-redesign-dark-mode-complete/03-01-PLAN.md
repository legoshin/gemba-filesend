<objective>
Reskin the entire download page (`src/app/download/page.tsx`) to the Gemba design
system already shipped on the home (Phase 1) and upload (Phase 2) pages, and replace
its toast-only failure handling with the D-01 "handled, not thrown" error states.
This closes PAGE-03.

Purpose: The download page is the recipient's trust moment — often a non-user who
just received a link. It must look like a sibling of the redesigned upload page and
handle dead-end links gracefully.
Output: A reskinned `download/page.tsx` whose four existing states use Gemba tokens,
the Icon wrapper, Chips, the inset-ring Card recipe, calm success, and the new D-03
secure-reassurance row — plus three terminal error-state cards and an inline
wrong-password error. Download/decryption behavior is unchanged.
</objective>

## Phase Goal (user story)

**As a** file recipient, **I want to** open a share link and download & decrypt my
file through a page that matches the Gemba design system and renders correctly in
light, dark, and system themes, **so that** the handoff feels trustworthy and
consistent with the rest of the app.

mvp-phase story formatting); no new capability is introduced — this phase is a
visual/token reskin plus theme-completeness verification only.</sub>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Share link URL fragment `#<key>` to client | The AES key arrives in the URL fragment, is read client-side only, and must never reach the server, logs, analytics, or persistent DOM state. This reskin must not change that. |
| Blob CDN / API response to client | Encrypted bytes + `meta` JSON cross here; already validated by the unchanged business logic (content-type, length, auth-tag minimum). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Information Disclosure | `fetchFileInfo` / `handleDownload` error copy + new D-01 state cards | mitigate | Error headlines/bodies are locked reassurance/diagnostic copy that never interpolates `keyBase64`, the URL fragment, or the presigned URL; acceptance criteria assert no key in copy/DOM attributes. |
| T-03-02 | Tampering | AES-GCM decrypt path (`decryptPacked`, `importKeyBase64`, streaming reader) | mitigate | Reskin is JSX/className/imports only; business logic preserved verbatim; acceptance criteria assert the crypto functions and their call sites are unchanged (success criterion 4). |
| T-03-03 | Information Disclosure | `aria-invalid` / inline password error | accept | Password value is never echoed into the DOM or error string; only a boolean flag drives the critical ring. No sensitive data exposed. |
| T-03-SC | Tampering (supply chain) | npm installs | accept | No package installs in this plan; only Icon/Chip components already vendored in Phases 1–2 are consumed. `components.json` registries unchanged. |
</threat_model>
