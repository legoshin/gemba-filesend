<phase_decisions>
Planner-locked defaults for this phase (from RESEARCH.md Assumptions Log + CONTEXT open questions). Flagged ones need user confirmation — see the plan-set return note.

- D-05-01: One-time code = 6-digit numeric, zero-padded, generated via `crypto.getRandomValues` % 1_000_000 (reuses the existing in-repo RNG idiom in `generateClientId()` / `server-storage.generateId()`; negligible modulo bias for a 10-min, 5-attempt code).
- D-05-02: Code TTL = 10 minutes. The authoritative expiry is an absolute `expiresAt` timestamp stored INSIDE the code's JSON payload and checked in app code; the Redis-level `ex` is set slightly longer (650s) purely as a GC backstop (RESEARCH Pitfall 3).
- D-05-03: Max 5 verify attempts per code; on the 5th failure the code is deleted (hard lockout → recipient must request a new code).
- D-05-04: [FLAG] verify-token is REUSABLE within a 30-min TTL (not single-use), so a multi-download link works without re-verifying each time.
- D-05-09: The 6-digit code is stored HASHED (`sha256Hex`) in Redis, mirroring the existing `passwordHash`/`salt` pattern (defense-in-depth against a Redis data exposure).
- D-05-10: [planner discretion] The verify-token + code domain helpers live in a NEW `src/lib/verification.ts` that composes `getRedisClient()` (via the widened `get`), keeping `redis.ts` the pure shared-client + download-counter module. RESEARCH suggested co-locating them in `redis.ts`; a dedicated module gives a clean, hermetically testable surface and matches the codebase's many-small-files convention.
- D-05-11: `verifyRequired` is DERIVED as `Boolean(meta.recipientEmails?.length)` everywhere — no separate stored boolean (RESEARCH Pitfall 5), exactly like `passwordProtected: Boolean(meta.passwordHash)`.
</phase_decisions>
