<objective>
Build the server-side notification path and prove it end-to-end with a tracer: a sender's
successful upload POSTs the real download link(s) to a new `/api/notify` endpoint, which sends
one Mailgun email per recipient (never a shared To/CC), reusing the existing bare-fetch Mailgun
sender and the shared sliding-window rate limiter.

Purpose: De-risk the whole phase on the first commit by wiring one path through every layer
(client success handler → /api/notify → rate-limit → per-recipient Mailgun send → fail-loud 500).
The architectural risk here is the LOCKED key-in-email exception (D-06-01): the full share link,
including the `#key` fragment, is POSTed to the server and relayed via Mailgun. Proving that path
works before expanding UX prevents an end-of-phase dead-end.

Output: `sendShareNotificationEmail` in mailgun.ts, `checkNotifyLimit` in rate-limit.ts,
`POST /api/notify` (+ testable `validateNotifyBody`), and a minimal notify POST call site wired
into the upload success handler.

Decision map (from 06-CONTEXT.md LOCKED decisions):
- D-06-01 key-in-email E2E exception (full link incl. #key relayed server-side) — LOCKED/approved.
- D-06-02 reuse mailgun.ts (add sendShareNotificationEmail mirroring sendVerificationEmail; no second sender).
- D-06-03 notify endpoint mirrors request-code shape: validate → rate-limit → Mailgun → fail-loud 500.
- D-06-04 fires only on successful upload; one email per recipient; failure non-blocking.
- D-06-07 per-recipient individual sends, never shared To/CC.
- D-06-09 iterate the upload's result links (multi-file safe; no single-link hard-code).
- D-06-10 no wire-format / encryption change beyond the approved key-in-email path.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → /api/notify | Untrusted JSON body: recipient emails + link URLs (the URLs carry the #key fragment). |
| /api/notify → Mailgun | Server relays a key-bearing download URL to a third-party email API over TLS (LOCKED exception D-06-01). |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-01 | Spoofing/DoS | POST /api/notify (open email relay abuse) | high | mitigate | Per-IP sliding-window `checkNotifyLimit` (RATE_LIMIT_NOTIFY_PER_MIN); recipients capped at 10; email length capped at 254. |
| T-06-02 | Tampering/Injection | validateNotifyBody link url | high | mitigate | Each url must parse as absolute http(s), be <=2048 chars, and match the request origin — blocks using notify as an arbitrary-link phishing relay. |
| T-06-03 | Information disclosure | recipient list exposure | high | mitigate | One Mailgun send per recipient (single `to`); never a shared To/CC (D-06-07). |
| T-06-04 | Injection (email header) | Mailgun `to`/`from` fields | medium | mitigate | Emails validated against EMAIL_RE (rejects whitespace/newlines); values set via FormData.set, not concatenated headers. |
| T-06-05 | Information disclosure | #key fragment transits server + Mailgun | high | accept | LOCKED, user-approved E2E exception (D-06-01); documented, not re-litigated. |
| T-06-06 | Availability | Mailgun/env misconfiguration | medium | mitigate | Fail-loud 500 + console.error on send failure (never a silent success); client treats it as non-blocking toast (upload preserved). |
| T-06-SC | Tampering | package installs | low | accept | No npm/pip/cargo installs in this phase — reuses existing bare-fetch Mailgun + Upstash limiter; no supply-chain surface added. |
</threat_model>
