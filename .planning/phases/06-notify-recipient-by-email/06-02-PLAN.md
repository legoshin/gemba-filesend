<objective>
Expand the proven notify path (06-01) into the real sender UX: a Notify Recipient toggle that
auto-enables Verify, a single shared recipient list rendered whenever either toggle is on, and an
interactive chip/tag input (removable [x] chips, inline rejection of invalid emails) built from the
existing shadcn Input + Badge — no new dependency.

Purpose: Deliver the locked interaction model (D-06-05 coupling, D-06-06 single shared list,
D-06-08 chip input) while keeping the tricky commit/reject/dedupe/cap logic in a pure, tested
helper so the component stays thin and no component-test infra is needed.

Output: `src/lib/recipient-emails.ts` (shared normalizer + validator + commit helper) with tests,
`RecipientChipInput` component, and the wired upload page (useNotify state, coupling, shared chip
list, updated guard/reset, notify POST over all result links).

Decision map (from 06-CONTEXT.md LOCKED decisions):
- D-06-04 fires only on successful upload; failure non-blocking; works encrypted + unencrypted.
- D-06-05 notify↔verify coupling (notify ON auto-enables verify; verify independently off-able; notify OFF does not force verify off).
- D-06-06 single shared recipient list feeding both; shown whenever either is on.
- D-06-08 interactive chip input (Enter/comma/blur commit, removable [x], inline invalid rejection, committed value = normalized string[]; reuse Input + Badge + parseRecipientEmails; no new dep).
- D-06-09 iterate the upload's result links (multi-file safe).
- D-06-10 no wire-format / encryption change.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user input → chip input | Free-typed email tokens committed into the shared recipient list. |
| upload client → /api/notify | The client sends the shared recipient list + all result links (incl. #key) to the server (validated server-side in 06-01). |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-07 | Tampering/Injection | chip input token commit | medium | mitigate | commitRecipientTokens validates each token against EMAIL_RE + length cap and rejects invalid entries inline; only normalized valid emails enter the list; server re-validates in /api/notify (defense in depth). |
| T-06-08 | Information disclosure | recipient list reuse for notify + verify | high | mitigate | Server sends one email per recipient (06-01, D-06-07); the client never places multiple recipients in a single visible field-to-header path. |
| T-06-09 | Availability | notify failure blocking upload | medium | mitigate | Notify POST isolated in its own try/catch; failure is a non-blocking toast, upload result always renders (D-06-04). |
| T-06-05 | Information disclosure | #key fragment in POSTed links | high | accept | LOCKED, user-approved E2E exception (D-06-01) — not re-litigated. |
| T-06-SC | Tampering | package installs | low | accept | No npm installs — chip input reuses existing Input + Badge; no supply-chain surface added (D-06-08). |
</threat_model>
