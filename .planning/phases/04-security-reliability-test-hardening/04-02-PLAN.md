## Phase Goal

**As a** person sharing a file through a Gemba link, **I want to** have abusive traffic and password brute-force throttled and my download limit enforced atomically, **so that** my link can't be hammered from one IP and can never be downloaded more times than I allowed — even under concurrent requests.

<objective>
Ship SEC-02 (per-IP rate limiting on upload + download + password attempts) and REL-01 (fix the download-counter race with an atomic Redis counter), both backed by ONE shared Upstash Redis store (D-10). These two hardenings are combined into a single plan because they share the Redis client module and both modify the same two API route files — splitting them would serialize edits to the same files across waves for no benefit.

Vertical slices delivered:
- Task 2 → a real end-to-end 429: the 11th upload from an IP inside a minute is throttled.
- Task 3 → download/password 429s AND the atomic counter: concurrent downloads can never exceed the limit (410 Gone once exhausted).

Purpose: close the abuse/brute-force gap (SEC-02) and the counter race (REL-01) with a single piece of new infra.
Output: `src/lib/redis.ts` (shared client + counter primitives), `src/lib/rate-limit.ts` (limiters), and the wired-in guards/seed/DECR in both API routes.

Decisions implemented: D-01 (Upstash @upstash/ratelimit + @upstash/redis), D-02 (moderate env-tunable thresholds; 429 + Retry-After), D-03 (in-memory limiting rejected), D-08 (atomic DECR on dl:{id}, 410 on negative), D-09 (Redis is the live counter authority; metadata keeps the original limit for display/expiry only), D-10 (one store serves both).
</objective>

| Boundary | Description |
|----------|-------------|
