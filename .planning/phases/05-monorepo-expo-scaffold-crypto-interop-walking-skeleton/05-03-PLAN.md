<objective>
Scaffold the Expo native app at apps/mobile so it can host the on-device crypto-interop gate in 05-04. Per D-08 the app uses Expo prebuild + a custom dev client + New Architecture (mandatory for react-native-quick-crypto v1.x, which is Nitro/New-Arch-only; Expo Go cannot load it), under identifier gemba.filesend for both platforms. Per D-09 expo-router and deep-link config are scaffolded now (not deferred), with a throwaway harness route that 05-04 wires to the golden vectors.

This plan installs the native dependency set flagged SUS/too-new in RESEARCH.md's Package Legitimacy Audit — so the FIRST task is a blocking human-verify of those packages before any install (T-05-SC). Per the D-05 correction, jest-expo is configured to unit-test ONLY the shared pure-TS core (it cannot execute the real JSI binding); the real native gate is Maestro-on-device in 05-04.

Environment note (RESEARCH Pitfall 4): this machine lacks full Xcode, Android SDK, Java, and watchman. The scaffold, config, and Metro bundle can be validated without a device; the actual "launches on iOS simulator + Android emulator" verification (APP-02) requires either local toolchain provisioning or an EAS dev-client build — that launch is finalized in 05-04 alongside the dev-client build. This plan proves the scaffold is sound (expo-doctor + a Metro export) and defers the device launch.

Purpose: A launch-ready Expo scaffold with a harness screen, safely-installed native crypto deps, and a jest-expo core pre-check.
Output: apps/mobile Expo app (gemba.filesend, expo-router, dev-client, New Arch), quick-crypto polyfill entry, jest-expo core test, and a verified supply-chain checkpoint.
</objective>
