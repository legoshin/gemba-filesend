<objective>
Close the walking-skeleton gate: make the native crypto adapter reproduce the exact frozen golden-vector bytes and prove it on a real device. This is the milestone's #1 risk, resolved before any uploader/downloader screen exists.

Per D-01/D-02b, packages/crypto/src/crypto.native.ts implements the same public async API as crypto.web.ts using react-native-quick-crypto's Node-style API — but because that library returns the 16-byte GCM tag SEPARATELY via getAuthTag() (unlike Web Crypto, which appends it automatically), the native adapter MUST concat the tag on encrypt and split it back off + setAuthTag() before final() on decrypt, to reproduce the exact [iv][ciphertext+tag] bytes. IV/salt randomness must come from quick-crypto's CSPRNG (randomBytes), never Math.random.

Per D-05 (corrected) the real gate runs on-device: the throwaway harness (scaffolded in 05-03) imports the REAL crypto.native.ts and the SAME frozen vectors.ts from 05-02, runs them, and renders per-vector PASS/FAIL plus a cross-decrypt result; a Maestro flow launches the EAS dev-client build and asserts the rendered PASS text. That dev-client build is also what proves APP-02 (launches on iOS simulator + Android emulator under gemba.filesend). A manual web-encrypt to native-decrypt round-trip (and reverse) is the final confidence check (D-04).

Environment reality (RESEARCH Pitfall 4 + Env Availability): this machine lacks full Xcode, Android SDK, Java, watchman, and Maestro, and EAS build needs an Expo account login — so the EAS build + device launch + Maestro run are human-gated. The native adapter and its jest-expo core-logic test are fully automatable now; the on-device assertion is the gated step.

Purpose: Prove byte-exact web-native crypto parity on real devices — the go/no-go for the rest of the milestone.
Output: crypto.native.ts (auth-tag correct), a wired harness, a Maestro interop flow, the EAS dev-client build, and a passing on-device + manual gate.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client crypto -> server | The AES key must never leave the client; native crypto must preserve the URL-fragment key model (CLAUDE.md) |
| web ciphertext <-> native ciphertext | The packed byte layout is the interop contract; an off-by-16 tag bug silently breaks it |
| host RNG -> IV/salt | Native randomness must be a CSPRNG, or IVs/salts become predictable |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-05-05 | Tampering / Information Disclosure | Native IV/salt randomness | mitigate | IV/salt generated via quick-crypto randomBytes (OpenSSL CSPRNG); never Math.random; asserted in Task 1 behavior |
| T-05-03 | Information Disclosure | AES key leaving the client on native | mitigate | Native crypto only exports the key as Base64URL for the URL fragment; no key sent to the server; encryption boundary preserved (CLAUDE.md) |
