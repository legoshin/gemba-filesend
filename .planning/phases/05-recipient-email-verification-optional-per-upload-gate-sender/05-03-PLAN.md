From 05-02 (server, already live):
- POST `/api/files/[id]/request-code` with JSON `{ email }` → always `{ sent: true }` (200) on success; never reveals membership.
- POST `/api/files/[id]/verify-code` with JSON `{ code }` → `{ verified: true, token }` (200) or `{ verified: false }` (403).
- GET `/api/files/[id]/meta` now returns `verifyRequired: boolean`.
- GET `/api/files/[id]` honours the `x-verify-token` request header (mirrors `x-password`).
- Upload accepts `recipientEmails: string[]` (≤10, lowercased) on the blob clientPayload and the fs x-meta payload.

Existing download state (src/app/download/page.tsx): `FileInfo` interface, `isMetaPayload` guard, `handleDownload` builds `headers` and sends `x-password`.
</interface_context>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| recipient browser → request-code / verify-code | untrusted email + code entered in the download UI |
| download page → GET /api/files/[id] | carries the minted x-verify-token header |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-09 | Information Disclosure | verify-token leak via URL/logs | low | mitigate | token sent ONLY as the x-verify-token request header on a same-origin fetch, never a query param (RESEARCH Security Domain) |
| T-05-01 | Information Disclosure | UI leaking recipient membership | high | mitigate | download UI shows the same neutral "a code may be on its way" message regardless of match, preserving the server's enumeration-safe response |
| T-05-12 | Spoofing | forged sender / phishing look-alike email | low | accept | reuses the user's existing verified Mailgun domain + MAILGUN_FROM; SPF/DKIM are a Mailgun-domain operator concern, out of app scope |
| T-05-SC | Tampering | package installs | low | accept | No new npm packages — UI reuses existing shadcn/Radix component layer |
</threat_model>
