<objective>
Make the storage + API layer describe MANY files under ONE share id and ONE key, without zipping and without touching the per-file wire format. Each file is stored separately under the one id; meta lists them; the read side serves any file by index; the download-limit counter stays one-per-id.

Purpose: This is the phase's backend foundation and the tracer slice — it proves the "one id / one key / per-file IV / multi-file meta / legacy-compatible read" architecture end-to-end at the data layer before any UI is rewritten (upload UI = Plan 02, download UI = Plan 03).
Output: Extended StoredMeta + resolveFiles() helper, per-index fs storage, a finalize route, index-addressable bytes route, meta route returning files[], and a round-trip test.
</objective>

- `GET /api/files/{id}/meta` — adds `files[]`, keeps legacy top-level fields
- `GET /api/files/{id}?index=N&consume=0|1` — index-addressable bytes/presign; one decrement per share
- server-storage: `writeBlobPartFromWebStream`, `openBlobPartReadStream`, `blobPartSize`, `partBlobPath`; blob-storage: `blobPartPathnamePrefix`
- Exported `MAX_FILES` cap
